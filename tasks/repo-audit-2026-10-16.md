## Sofort-Befund vor allem anderen

Der Working-Tree-`.gitignore` ignoriert `.env` und `data/**` **nicht mehr**. `git diff .gitignore`
zeigt 143 geaenderte Zeilen: der komplette committete Block ab "Runtime database data (never
commit)" (Whitelist `/data/**`, `.env`, `.env.local`, `docker-compose.override.yml`, `*.bak`,
`*.dmp`, `node_modules/`, die `!artefacts/*.log`-Ausnahmen) ist durch ein Toolkit-Template ersetzt
("AI toolkit symlinks - generated by init-repo.sh"). `git check-ignore .env data/xchange/wallet_prod`
liefert nichts.

Folge: `git status` listet `.env` (ORACLE_PWD), `data/xchange/wallet_prod/`,
`data/xchange/pdbclone_p4_keys.exp` (exportierte TDE-Keys), `data/seclab/` als untracked. Ein
`git add -A` wuerde Keystores und Passwoerter committen - im Kommentar des Originals steht zu Recht,
dass das nicht durch spaeteres Loeschen heilbar ist. Das ist genau das Muster aus der Regel "Tool
Safety: Block Replacement". Empfehlung: vor dem naechsten Commit auf `feat/seclab` den committeten
Inhalt key-aware zurueckmergen (Toolkit-Zeilen behalten, Whitelist-Block wiederherstellen), dann
`git check-ignore -v .env data/xchange/wallet_prod` muss wieder treffen.

## Zielbild

### Prinzip

Ein **Use Case** ist eine benannte, idempotente Folge von Schritten auf Basis der bestehenden
Common-Skripte. Ein **Service** ist "Image + Liste von Use Cases + PDB-Name". Derselbe Runner laeuft
(a) beim ersten Start aus dem Setup-Verzeichnis eines Services und (b) nachtraeglich gegen jeden
laufenden Oracle-Free-Container, auch einen selbst gestarteten Vanilla-Container.

### Ebenen

<!-- markdownlint-disable MD013 MD060 -->
| Ebene | Inhalt | Voraussetzung | Einstieg |
| --- | --- | --- | --- |
| L0 | Vanilla `container-registry.oracle.com/database/free` | nur Docker/Podman | `docker run ...` oder `make up-free` |
| L1 | L0 + ein oder mehrere Use Cases (TDE, Audit, Demo-Schemas, seclab) | laufender Container, Repo-Checkout auf dem Host | `make apply UC=tde TARGET=<container>` |
| L2 | L1 + OraDBA-Umgebung (oradba-Tools, rlwrap, `/opt/oracle/network/admin`, Wallet-Persistenz) | `make build` oder nachtraeglich per Use Case `oradba-env` | `make up-labdb` |
<!-- markdownlint-restore -->

Regel: Ein Use Case der Ebene `db` darf nichts aus L2 voraussetzen (kein `/opt/oracle/network`,
kein `/opt/oracle/dbconfig`-Bind-Mount, kein oradba). Nur Use Cases mit `LEVEL=oradba` duerfen das.

### Manifest

Format: Shell-`KEY=value`, weil im Container weder `yq` noch Python vorausgesetzt werden darf und
der Runner Bash ist. Beispiel `config/usecases/tde/usecase.conf`:

```bash
NAME=tde
DESCRIPTION="Software keystore with WALLET_ROOT, auto-login, master key"
LEVEL=db                       # db | oradba
SCOPE=cdb                      # cdb | pdb
REQUIRES=""                    # andere Use Cases, z.B. "ts-users"
ENV_REQUIRED=""                # z.B. "SECLAB_USER_PWD SECLAB_SCOTT_PWD"
RESTART=instance               # none | instance - wird vor dem Lauf angekuendigt
DEFAULT_PDB=FREEPDB1
WALLET_BASE_DEFAULT='${ORACLE_BASE}/oradata/dbconfig/${ORACLE_SID}'
```

`steps` mit einer Zeile pro Schritt, `${PDB}` wird ersetzt, Bezeichner `cdb|pdb|sh`:

```text
cdb define_wallet_root_base.sql
cdb idenc_wroot.sql ${WALLET_BASE}
cdb restart_instance.sql
cdb csenc_swkeystore.sql
cdb csenc_master.sql
cdb restart_instance.sql
cdb ssenc_info.sql
```

### Runner

In-Container: `config/common/scripts/apply_usecase.sh <name> [--pdb X] [--dry-run]`

- liest Manifest, prueft `REQUIRES` (rekursiv, ueber Zustandsmarker) und `ENV_REQUIRED` (fehlt
  etwas: Abbruch mit Name der Variable, kein stilles Weiter),
- fuehrt jeden Schritt ueber `run_sql_script.sh` aus (`cdb` ohne `-p`, `pdb` mit `-p ${PDB}`),
  `sh`-Schritte als eigener Prozess,
- schreibt bei Erfolg `/opt/oracle/oradata/oflab/state/<name>[_<pdb>].done` (auf dem Volume,
  ueberlebt Container-Neuanlage) und Logs nach `/opt/oracle/oradata/oflab/logs/`,
- gibt am Ende aus, was gelaufen ist, was uebersprungen wurde (mit Grund) und was neu gestartet hat.

Host-seitig: `scripts/oflab apply <usecase> [--container NAME] [--pdb X] [--engine docker|podman]`

1. prueft, dass der Container laeuft und eine Oracle-Free-DB enthaelt (`checkDBStatus.sh`),
2. `docker cp config/common/scripts` nach `/opt/oracle/common/scripts` und den Use Case nach
   `/opt/oracle/common/usecases/<name>` - dieselben Pfade wie in den Services, damit die bestehenden
   `@/opt/oracle/common/scripts/...`-Aufrufe unveraendert gelten,
3. `docker exec -u oracle -e VAR ... <container> apply_usecase.sh <name>`; Passwoerter nur per
   `-e VAR` (Wert aus Host-Umgebung oder `op read`), nie als Argument,
4. Exit-Code und Zusammenfassung zurueck. `make apply UC=tde TARGET=x` ist ein duenner Aufruf davon.

Service-Seite: Compose mountet fuer alle Services dasselbe `config/services/setup` als
`/opt/oracle/scripts/setup` und setzt `OFLAB_USECASES="base-config pdb audit ts-users demo-hr"` und
`OFLAB_PDB=LABPDB1`. `00_apply_usecases.sh` ist in einer Subshell gekapselt (sourced-Falle) und ruft
`apply_usecase.sh` je Eintrag auf. Damit entfallen die 72 Service-Wrapper; die einzige Service-Datei
ist die Compose-Definition.

# Ich habe einen eigenen Oracle Free Container "myfree" und will TDE

### Makefile

- 48 Per-Service-Targets durch eine Pattern-Regel ersetzen:

  (oder sechs Zeilen `up-%: ; @$(MAKE) up SERVICE=$*`). Aufrufe wie `make up-labdb` bleiben
  gueltig. Verlust: Bash-Completion zeigt Pattern-Targets nicht mehr an; `make help` listet sie.
- `SERVICES` und die Help-Tabelle (`Makefile:45,94-103`) aus einer Quelle ableiten:
  `docker compose config --profiles` fuer die Liste, Beschreibung aus einem Label

- Neue Targets: `usecases`, `apply UC= TARGET= [PDB=]`, `status TARGET=`, `up-free` (L0-Container
  aus dem Vanilla-Image mit benanntem Volume).

## Nachtrag - Container-Runtimes (gemessen 2026-10-16, Session feat/seclab)

Frage: Muss alles auch mit "nur" Colima oder Podman laufen, und welche Einschraenkungen gibt es?
Geklaert vor der Umsetzung des Plans, mit Messungen auf Apple Silicon (arm64):

<!-- markdownlint-disable MD013 MD060 -->
| Runtime | Ergebnis | Belegt durch |
| --- | --- | --- |
| Docker Desktop | seclab-Service und `apply_usecase.sh` laufen, 11/11 PRESENT | erster Start 2 min, zweiter Start 7 s, Vanilla-Pfad 18 s |
| Colima 0.10.3 (`--vm-type vz --mount-type virtiofs`, 4 CPU, 6 GiB) | laeuft, sobald das Repo unter `$HOME` liegt | `colima start` 40 s, Pull 128 s, `make build` 88 s, `make up-seclab` 130 s, Vanilla 18 s |
| Podman | nicht verifiziert (auf dem Testhost nicht installiert) | nur dokumentiert in `doc/container-runtime-runbook.md` |
<!-- markdownlint-restore -->

Einschraenkungen, die der Plan beruecksichtigen muss:

- Colima mountet standardmaessig nur `$HOME`. Ein Bind-Mount von ausserhalb wird in der VM still zu einem
  leeren Verzeichnis; der `TNS_ADMIN`-Symlink zeigt ins Leere, DBCA bricht mit `DBT-60127` ab, der
  Container startet in einer Schleife neu. `scripts/check_requirements.sh` prueft das jetzt per
  `colima ssh -- test -f <repo>/docker-compose.yml` (Datei statt Verzeichnis, weil Docker fehlende
  Bind-Quellen als Verzeichnisse anlegt - der erste Check mit `test -d` war deshalb falsch gruen).
- Mit virtiofs erscheinen Dateien der Container-UID 54321 auf dem Host als der eigene User und bleiben
  schreibbar - kein UID-Problem unter Colima/vz.
- Docker-Kontext: `colima start` schaltet den Kontext um. Alle Skripte nutzen `docker` und respektieren
  `DOCKER_CONTEXT`; zwei Engines koennen nicht denselben Host-Port binden.
- `docker cp` / `docker exec` (Vanilla-Pfad) haengen nicht an den VM-Mounts - der Use-Case-Runner ist
  deshalb die robusteste Variante fuer jede Runtime.
- Podman (erwartet, nicht gemessen): docker-CLI und `docker-compose` gegen den Podman-Socket statt
  `podman-compose`, weil das Repo Compose-Profile, YAML-Merge-Keys und `deploy.resources.limits`
  nutzt; rootful Machine wegen der UID der Bind-Mounts.

Konsequenz fuer den Plan: Phase 1 (Runner) zuerst, weil `docker cp`/`docker exec` auf allen drei
Runtimes gleich funktioniert; Bind-Mount-basierte Services bleiben an die Mount-Regeln der VM gebunden.
Ein Podman-Lauf (Service und Vanilla-Pfad) gehoert als Verifikationsschritt in Phase 1.
